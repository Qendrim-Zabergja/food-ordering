Food Ordering — AI Development Record

The direction given at each decision point during development, and the outcome.

Laravel 13 · React 19 · MySQL 8 114 tests · 330 assertions 14 exchanges

Development used AI assistance. This document records the direction given at each decision point and the outcome it produced, edited for clarity and length; it is not a verbatim export. The unedited session log is submitted separately.

01 Scope and working constraints

Developer

We are building a food ordering application on Laravel, React and MySQL, exposed as a REST API. Scope: administrator authentication, a product catalogue with categories, a cart supporting quantity changes and removal, order creation, a customer's own order history, order status, and an admin panel for products and orders.

Three constraints before we start. Take the installation commands from the official Laravel and React documentation rather than from memory, and leave them for me to run. Structure the repository as a monorepo. Apply our existing backend engineering standards — model naming, UUID exposure and authorisation.

Response

Retrieved the Laravel 13 installation and Sanctum documentation and the React guidance, read the standards files, then checked the local toolchain and reported PHP 8.3.14 against Laravel 13's 8.3–8.5 requirement before recommending anything.

Proposed an npm-workspace monorepo with the API and the single-page application as separate workspaces sharing only the HTTP contract.

04 Shared foundations before features

Developer

Put the base layer in place before any entity work — the pieces every model, controller and resource will depend on — and follow the patterns already used in our other Laravel projects rather than inventing new ones.

Response

Ported five base classes from the existing production codebase so the request contract matches the organisation's other APIs:

  • HasUuid — assigns the external UUID on create, with getRouteKeyName() in the trait so no model can omit it
  • Controller::loadRelationships() — the single place that interprets ?with=
  • QueryFilters, Filterable, QuerySorting — the Model::filter($filters) pattern used by every index endpoint
  • BaseResource — parent of all resources
  • PermissionSlug, RoleSlug — native PHP backed enums

Native enums replaced the package-based enum the standards describe: no third-party dependency, no Laravel 13 compatibility question, and type safety at the call site. The invariant the standard protects — permission strings are never raw literals — is unchanged.

06 Generated code held to the project's conventions

Developer

Use our scaffolding tool for the product entities, as the standards require, then verify the result against the conventions before we build on it.

Response

The tool reported success while having written PHP that would not parse — it assumed a different permission-enum structure to the one this project uses:

PHP Fatal error: Cannot redefine class constant
                 PermissionSlug::VIEW_PRODUCT_CATEGORIES

PHP Parse error: syntax error, unexpected token ","
                 in PermissionSeeder.php on line 44

Eleven further defects were found in its output, including uuid in $fillable — which would have allowed a client to choose its own identifier — a table named productcategories rather than product_categories, and routes registered outside the authenticated group. All of it was rewritten against the project's conventions.

A tool's own success report is not evidence. Checking that the project still parsed afterwards is what caught it, and a proposed amendment to the standards was written up so the next person checks the files a tool edits, not only the ones it writes.

07 Money, and when a price becomes final

Developer

Decide how prices are stored and at which point in the flow a price becomes final. An order must not be able to change value after it has been placed.

LocationBehaviourReasoning
ProductCurrent priceIt is the menu
Cart lineReads the product price liveA cart remembering an old price would quietly charge it
Order lineA copy, written at checkoutAn order records what was agreed

Prices are stored as integer cents throughout; a decimal or float rounds, and rounding errors surface once quantities and totals are involved. Order lines duplicate the product name alongside the price, and the foreign key is nullOnDelete rather than cascadeOnDelete — removing a product from the menu must never delete the record of having sold it. Two tests assert that renaming, repricing or deleting a product leaves past orders unchanged.

08 Authentication, and an error the tests could not reach

Developer

Implement registration, login, logout and current-user endpoints. Before calling it done, exercise them against a running server rather than relying on the test suite.

Response

With the suite passing at 77 tests, a request from a browser returned:

GET /api/products  (Accept: */*)
→ 500  "Route [login] not defined."

Laravel's Authenticate middleware redirects unauthenticated users to a login route, which an API-only application does not have. Laravel's test client always sends Accept: application/json, which takes the JSON path and never exercises the redirect — so no test could have caught it. A browser takes the broken path, meaning every unauthenticated request from the React application would have hit it.

Fixed by returning no redirect target for guests, with a regression test that sends Accept: */* explicitly. Registration always assigns the customer role and never reads one from the payload; login returns an identical error for a wrong password and an unknown address, so it cannot be used to enumerate accounts. Both endpoints are rate limited.

09 The order lifecycle

Developer

I am considering reducing the order statuses to Confirmed, Preparing and Completed. Make the case for or against before changing anything.

Response

The case against removing pending: every order is created pending, so without it an order would be born "Confirmed" — the restaurant accepting it before anyone had looked, with no state for "ordered, not yet decided" and therefore no way to reject one. It also drives customer cancellation, which is permitted while an order is pending or confirmed and not after.

All five were kept. The follow-up concerned how the interface presented them:

Developer

Keep the five, but an administrator only ever sees three options. The interface should show the whole lifecycle and where an order currently sits in it.

The three buttons were the next legal steps rather than the status list — but the observation held: nothing showed the pipeline as a whole. Added pipeline(), step() and hasReached() to the OrderStatus enum, exposed step, total_steps and a progress array in the API response, and rendered a progress indicator on the order page with a "Step 3 of 5" column in the table.

Cancelled is modelled as leaving the pipeline rather than completing it, so a cancelled order shows no misleading 5-of-5 bar. The transition rules live only on the server; the React components render what the API sends, so changing the lifecycle requires no frontend change at all.

10 Frontend architecture

Developer

Set up the React application with the same discipline as the backend: typed models rather than raw response objects, route and permission constants rather than string literals, and a single place where the token and error handling live.

Response

One axios instance carries the bearer token and handles 401 centrally; API responses are hydrated into model classes before reaching a component; routes and permissions are constants.

Two constraints came from the toolchain rather than preference. The TypeScript configuration sets erasableSyntaxOnly, which forbids enum — so the constants are as const objects, which read identically at the call site. And strict was absent from the scaffold and was enabled, since typed models are worth little without strictNullChecks.

ESLint rejected a real defect during this work: setState called synchronously inside an effect body, causing a cascading render. It was fixed by deriving the initial state rather than by suppressing the rule.

11 Consolidating the orders screens

Developer

The separate Admin section for orders looks redundant. An administrator should open Orders, select an order and change its status there, next to the items and delivery details.

Response

Investigating it surfaced a defect: /api/orders already returned every order to a user holding manage-orders, because the controller unscopes for that permission — but the page heading still read "Your orders". The admin screen existed only to display the same rows under a correct heading.

The duplicate screen was removed in favour of one orders page that adapts to the viewer — customer column, status filters and a Manage action for administrators, a plain list for customers. Status transitions moved onto the order detail page. No backend change was required, because the API had been scoping correctly the whole time.

12 An operational view

Developer

Add a filter to the orders page for administrators: orders placed today whose status is not completed.

Built as two composable query filters rather than one fixed flag:

?filter[placed_on]=today
?filter[exclude_status][]=completed

"Placed today" and "not finished" are independent questions, so a single combined filter would have meant a new endpoint for the next variation. Administrators land on this view by default, since it is the reason to open the page during service. cancelled is excluded alongside completed, as the view answers what is still to do and a cancelled order is as finished as a delivered one.

Six tests cover it, including one asserting that a customer using the same filters is still scoped to their own orders — the filter cannot be used to widen access.

13 Interface review

Developer

Two things in the header read wrongly. The signed-in user's name is styled like a navigation button, and it belongs at the right-hand edge rather than beside the links. Separately, the admin section is labelled "Admin", which describes who it is for rather than what it does.

The name became an account block — avatar, name and email — pinned to the right of the header, with the navigation centred between the brand and it. "Admin" became "Manage menu": with orders now handled from the orders page, that section edits exactly one thing, and the link is already hidden from anyone without the permission.

Neither was detectable by automated checks. Both required looking at the running application and noticing it communicated the wrong thing.

14 Extending the permission model

Developer

Document what is involved in adding a new role and granting it permissions, including anything that could go wrong.

Adding a role is an enum case, two match arms the compiler will not let you skip, and a seeder run. Four constraints were documented alongside it:

  1. hasPermissions() requires all permissions to come from a single role, so two narrow roles do not combine into a broad one
  2. defaultPermissions() grants but never revokes
  3. permissions:sync grants new permissions only to full-access roles
  4. Roles are defined in code rather than managed at runtime — a scope decision, recorded as such

The first is the one that would cause a real bug, and it is covered by a test asserting that a user holding two narrow roles is refused the combination.
